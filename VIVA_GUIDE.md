## 🏛️ General System Architecture & OOP Principles

### Layered Architecture
Every component follows a clean 4-layer enterprise pattern:
1. **Entity Layer (`entity/`):** Represents the database domain models using JPA annotations. Demonstrates encapsulation and inheritance.
2. **Repository Layer (`repository/`):** Interfaces extending `JpaRepository<T, ID>` that handle SQL query generation, search finders, and persistence.
3. **Service Layer (`service/`):** Contains the business logic contracts (`interface`) and transactional implementations (`Impl`). Enforces validation rules, lead times, capacity, and polymorphism.
4. **Controller Layer (`controller/`):** REST API endpoints (`@RestController`) consuming JSON requests and returning standardized `ApiResponse<T>` envelopes.

### The Four Pillars of OOP in Crumb
- **Encapsulation:** All class attributes are `private`. Getters/Setters generated by Lombok mediate access while keeping data secure and validating state transitions.
- **Inheritance:** Handled via JPA Single Table Inheritance (`InheritanceType.SINGLE_TABLE`) with a discriminator column, mapping specialized domain subtypes into a clean relational model.
- **Polymorphism:** Abstract methods in base classes are overridden by subclasses to implement specialized pricing rules, discounts, quotas, and formatting.
- **Abstraction:** Abstract base classes specify common state and behavior templates without implementation details; service interfaces decouple client controllers from data storage technologies.

## 👤 Component 1: Customer & Authentication

**Package:** `com.crumb.customer`  
**Owner:** Member 1 (Customer & Identity Lead)

### 1. Plain-English Explanation
This component manages customer registration, secure login with BCrypt password hashing, session tracking, personal profile updates, and role-based permissions (`CUSTOMER` vs `ADMIN`). It models two distinct tiers of customer: **Regular Customers** and **Premium (VIP Gold) Customers**.

### 2. Classes & Hierarchy
- `Customer` (abstract entity): Base class containing ID, name, email, hashed password, phone, address, role (`CUSTOMER`, `ADMIN`), active flag, and abstract methods `calculateDiscount()`, `getCustomerBadge()`, and `getMaxActiveBookings()`.
- `RegularCustomer` (subclass): Standard retail shopper with 0% order discount and standard booking quotas.
- `PremiumCustomer` (subclass): VIP Gold member entitled to a 10% discount on all orders, waived delivery charges, and priority booking quotas.
- `CustomerRepository`: JPA repository with `findByEmail()` and search query finders.
- `CustomerService` / `CustomerServiceImpl`: Business logic handling BCrypt hashing, session creation, profile editing, and dynamic tier upgrades.
- `CustomerAuthController`: Public `/api/auth` endpoints for login, signup, logout, and `/me`.
- `CustomerController`: Protected `/api/customers` endpoints for profile management and admin customer moderation.

### 3. CRUD Flow
- **Create:** User registers via modal form (`POST /api/auth/register`). The service checks email uniqueness, hashes the password via BCrypt, instantiates either `RegularCustomer` or `PremiumCustomer`, saves it to MySQL, and logs them into the HTTP session.
- **Read:** User views their profile via `GET /api/customers/{id}` or `GET /api/auth/me`. Admin searches all customers via `GET /api/customers?query=...`.
- **Update:** User updates their phone number or address via `PUT /api/customers/{id}`. Customer can also dynamically upgrade their account to VIP Gold via `POST /api/customers/{id}/upgrade`.
- **Delete:** Admin can soft-suspend accounts via `PUT /api/customers/{id}/status` or permanently delete them via `DELETE /api/customers/{id}`.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: Why did you use an abstract `Customer` class instead of a single concrete class with an enum?**  
*Answer:* Using an abstract `Customer` class with concrete subclasses (`RegularCustomer` and `PremiumCustomer`) leverages object-oriented polymorphism. Different customer tiers have different behaviors (e.g. discount calculation, booking limits, delivery fee waivers). Subclassing allows these behaviors to be overridden cleanly without cluttered `if/else` or `switch` statements, adhering to the Open/Closed Principle.

**Q2: How is JPA inheritance configured for Customer?**  
*Answer:* We used `InheritanceType.SINGLE_TABLE` on the `Customer` class with `@DiscriminatorColumn(name = "customer_type")`. In the database, all customers share the `customers` table, and Hibernate automatically handles instantiation of `RegularCustomer` (value `REGULAR`) or `PremiumCustomer` (value `PREMIUM`) based on the discriminator column.

**Q3: How does your code satisfy the Encapsulation principle?**  
*Answer:* All fields in `Customer` (like `passwordHash`, `email`, `fullName`) are marked `private`. They can only be accessed or modified through getters and setters. Sensitive fields like `passwordHash` are never exposed in `CustomerResponse` DTOs sent to the client browser.

**Q4: How are passwords stored securely in the database?**  
*Answer:* We use `BCryptPasswordEncoder` from Spring Security Crypto. Passwords are never stored in plain text. On registration, the raw password is salted and hashed (`passwordEncoder.encode(rawPassword)`), and on login, it is verified using `passwordEncoder.matches(rawPassword, storedHash)`.

**Q5: How does session management work between frontend and backend?**  
*Answer:* We use Spring Boot's standard HTTP Session via `SessionAuthHelper`. When a user logs in, their ID, name, email, and role are saved into the `HttpSession`. A secure cookie `CRUMB_SESSION_ID` is issued to the browser, allowing the backend to verify the user on subsequent requests.

**Q6: What happens if a regular customer tries to access admin customer management APIs?**  
*Answer:* The controller invokes `SessionAuthHelper.requireAdmin(session)`. If the session is missing or the role is not `ADMIN`, it immediately throws a `ForbiddenException` (HTTP 403), which the `GlobalExceptionHandler` converts into a standardized error response.

**Q7: Can a customer upgrade their tier at runtime? How is this handled?**  
*Answer:* Yes. Through `CustomerService.upgradeToPremium(id)`, the service retrieves the `RegularCustomer`, creates a new `PremiumCustomer` copying over identity fields and history, and updates the repository. On their next checkout, polymorphism immediately grants them the 10% VIP discount.

**Q8: What DTOs did you create for the customer component and why?**  
*Answer:* We created `RegisterRequest`, `LoginRequest`, `CustomerUpdateRequest`, and `CustomerResponse`. DTOs (Data Transfer Objects) decouple internal database entities from external API contracts, prevent over-posting vulnerabilities, and enable Bean Validation (`@NotBlank`, `@Email`, `@Size`).

**Q9: Where is polymorphic method overriding used in Customer?**  
*Answer:* In methods `calculateDiscount(double subtotal)` and `getDeliveryFeeDiscount()`. In `RegularCustomer`, `calculateDiscount` returns `0.0`. In `PremiumCustomer`, it overrides this to return `subtotal * 0.10` (10% savings).

**Q10: How does the frontend know which elements to show for guests vs logged-in users?**  
*Answer:* On every page load, `customer.js` calls `GET /api/auth/me`. If a valid user is returned, it toggles elements with classes `.guest-only` and `.user-only`, updates the avatar and name, and if the user has role `ADMIN`, reveals the `.admin-only` shortcut button.

## 🥖 Component 2: Bakery Products & Inventory

**Package:** `com.crumb.product`  
**Owner:** Member 2 (Catalog & Product Lead)

### 1. Plain-English Explanation
This component manages the bakery's artisan offerings, organized into three distinct product families: **Cakes**, **Pastries**, and **Hearth Breads**. It powers the storefront menu, category chips, live keyword search, quick-view modal, stock tracking, and volume-based pricing rules.

### 2. Classes & Hierarchy
- `BakeryProduct` (abstract entity): Contains base fields: ID, name, description, basePrice, stockQuantity, imageUrl, allergens, available flag, and abstract method `calculateFinalPrice(quantity)`.
- `Cake` (subclass): Adds attributes `layers` and `frostingType`. Implements a 5% party discount when buying 2 or more cakes.
- `Pastry` (subclass): Adds attributes `pastryType` (e.g. Croissant, Tart) and `warmable`. Implements a pastry-box volume discount: 10% off for 6+ items, 15% off for 12+ items.
- `Bread` (subclass): Adds attributes `loafWeightGrams` and `sourdough` flag. Implements a 5% bundle discount for 3+ loaves.
- `ProductRepository`: Queries for catalog search, category filtering, and available items.
- `ProductService` / `ProductServiceImpl`: Handles catalog retrieval, price calculations, and admin product CRUD.
- `ProductController`: REST endpoints at `/api/products`.

### 3. CRUD Flow
- **Create:** Admin clicks "Add New Product" in `admin.html`, selecting Cake, Pastry, or Bread. Subclass-specific input fields dynamically appear. On submit (`POST /api/products`), the service instantiates the appropriate subclass and saves it to MySQL.
- **Read:** Storefront visitors fetch items via `GET /api/products?keyword=...&type=...`. Quick-view modal calls `GET /api/products/{id}`.
- **Update:** Admin edits price, stock, or description via `PUT /api/products/{id}`.
- **Delete:** Admin removes a product via `DELETE /api/products/{id}` or toggles its storefront visibility via `available=false`.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: How do you handle different types of bakery items with unique properties?**  
*Answer:* We use inheritance. `BakeryProduct` is an abstract base entity, while `Cake`, `Pastry`, and `Bread` are subclasses that add specialized properties (e.g., `layers` for cakes, `warmable` for pastries, `loafWeightGrams` for bread).

**Q2: What JPA inheritance strategy was chosen for products and why?**  
*Answer:* `InheritanceType.SINGLE_TABLE` with `@DiscriminatorColumn(name = "product_type")`. It avoids costly multi-table joins, delivers the fastest query performance for storefront browsing, and keeps the database schema clean and easy to maintain.

**Q3: Explain how Polymorphism is demonstrated in the product catalog.**  
*Answer:* In the `calculateFinalPrice(int quantity)` method. When an order item is evaluated, the runtime polymorphism automatically invokes `Cake.calculateFinalPrice()`, `Pastry.calculateFinalPrice()`, or `Bread.calculateFinalPrice()`. Each subclass calculates volume discounts differently according to realistic bakery practices.

**Q4: How does the quick-view modal calculate discounts on the fly?**  
*Answer:* It calls `GET /api/products/{id}/price?quantity=N`. The controller delegates to `ProductService.calculateFinalPrice(id, qty)`, which looks up the product and executes the polymorphic calculation, returning the final price directly to the UI.

**Q5: How is data seeding handled for the product catalog?**  
*Answer:* `ProductServiceImpl.initSampleProducts()` is invoked on application startup by `DataSeeder` (a Spring `CommandLineRunner`). If the repository is empty, it populates 11 authentic artisan items with high-resolution Unsplash food photography.

**Q6: What happens if an item runs out of stock?**  
*Answer:* The `stockQuantity` attribute tracks available inventory. During order checkout, the service verifies inventory and deducts stock. When stock reaches 0, the UI badge shows "Out of Stock" and prevents further ordering.

**Q7: Why are allergen tags important in this entity?**  
*Answer:* Real-world bakery applications must ensure food safety. We encapsulated the `allergens` field (e.g. "Gluten, Dairy, Eggs, Soy") in the `BakeryProduct` base class so all products inherit it, and it is surfaced in both the card previews and quick-view modal.

**Q8: How does live catalog search work on the frontend?**  
*Answer:* In `product.js`, an input listener with a 250ms debounce timer filters products based on name, description, and category. It dynamically re-renders product cards without requiring a full page refresh.

**Q9: How is product deletion protected against unauthorized users?**  
*Answer:* In `ProductController.deleteProduct()`, the method begins with `SessionAuthHelper.requireAdmin(session)`. Only authenticated users holding the `ADMIN` role can execute `DELETE` or `POST` product operations.

**Q10: What Bean Validation rules are applied when creating a product?**  
*Answer:* In `ProductRequest`, fields have `@NotBlank` on name, `@PositiveOrZero` on basePrice and stockQuantity, and `@NotNull` on productType. Any violation triggers a 400 Bad Request handled by `GlobalExceptionHandler`.

## 🎂 Component 3: Custom Cake Studio

**Package:** `com.crumb.customcake`  
**Owner:** Member 3 (Custom Cake Lead)

### 1. Plain-English Explanation
This component empowers customers to design bespoke celebration cakes through an interactive 2D cake builder. Customers select occasions, sponge flavors, tier count (1 to 5 tiers), custom piping inscriptions, and decorative accents (candles, floral cascades, 24k gold leaf). It features a dynamic price estimation engine and lead-time scheduling validation.

### 2. Classes & Hierarchy
- `CustomCake` (abstract entity): Contains base fields: reference number, customer association, flavor, tiers, inscription, special instructions, required delivery date, estimated price, status (`PENDING`, `CONFIRMED`, `IN_PRODUCTION`, `COMPLETED`, `CANCELLED`), and abstract method `calculateEstimatedPrice()`.
- `BirthdayCake` (subclass): Adds `includeCandles` and `numberTopperAge`. Minimum 2-day lead time.
- `WeddingCake` (subclass): Adds `floralArrangement` and `champagneFondant`. Multi-tier pricing with a minimum 5-day lead time for intricate sugarcraft.
- `CelebrationCake` (subclass): Adds `goldLeafAccent` and `corporateLogoText`. Minimum 3-day lead time.
- `CustomCakeRepository`: Finders for customer orders, status filtering, and reference code lookup.
- `CustomCakeService` / `CustomCakeServiceImpl`: Validates lead times, calculates estimates, processes bookings, and updates kitchen status.
- `CustomCakeController`: REST endpoints at `/api/custom-cakes`.

### 3. CRUD Flow
- **Create:** Customer customizes cake options and clicks "Book Bespoke Cake" (`POST /api/custom-cakes`). The service checks lead-time constraints against `requiredDate`, calculates the polymorphic price, saves the entity, and issues a tracking reference (e.g. `CAKE-20261025-ABCD`).
- **Read:** Customer reviews booking history via `GET /api/custom-cakes/my`. Admin reviews all pending requests via `GET /api/custom-cakes/{id}`.
- **Update:** Admin transitions cake status (`CONFIRMED` ➔ `IN_PRODUCTION` ➔ `COMPLETED`) via `PUT /api/custom-cakes/{id}/status`.
- **Delete:** Customer or admin can cancel an unbaked cake via `PUT /api/custom-cakes/{id}/cancel`.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: How does the custom cake builder prevent impossible last-minute bookings?**  
*Answer:* In `CustomCakeServiceImpl.createRequest()`, the service calculates the required advance preparation days via `getMinLeadDays()`. For example, a 3-tier Wedding Cake requires at least 5 days notice. If `requiredDate` is earlier, a `BadRequestException` is thrown. The frontend datepicker also disables dates prior to this threshold.

**Q2: How does the live price preview work without creating a database record?**  
*Answer:* The client calls `POST /api/custom-cakes/preview` sending the user's current configuration. The controller invokes `customCakeService.calculatePreviewPrice(request)`, which executes the polymorphic calculation in memory and returns the estimated cost instantly.

**Q3: How does Polymorphism calculate prices for different cake types?**  
*Answer:* `calculateEstimatedPrice()` is defined abstractly in `CustomCake`. `WeddingCake` starts with a premium base fee of $120 and adds $35 per extra tier plus floral styling. `BirthdayCake` starts at $50 plus $20 per tier and optional candles. `CelebrationCake` starts at $75 plus gold leaf options.

**Q4: How is the visual 2D cake preview rendered on the frontend?**  
*Answer:* In `customcake.js`, `renderVisualizer()` dynamically builds HTML elements inside the preview stage. It generates sponge layers corresponding to `state.tiers`, applies frosting colors based on the selected flavor, and attaches the appropriate emoji/accent topper.

**Q5: What unique identifier is generated for custom cakes?**  
*Answer:* A human-friendly reference string like `CAKE-20261025-XXXX`, where `XXXX` is a randomized alphanumeric hash. This allows both customers and kitchen staff to reference the custom order easily.

**Q6: What happens if a customer attempts to cancel a cake already "IN_PRODUCTION"?**  
*Answer:* In `CustomCakeServiceImpl.cancelRequest()`, the method verifies whether the cake has already entered production. If status is `IN_PRODUCTION` or `COMPLETED`, cancellation is blocked with a `BadRequestException` because ingredients and artisan labor have already been committed.

**Q7: How are customer notes and dietary requests encapsulated?**  
*Answer:* The `specialInstructions` field in `CustomCake` captures customer specifications (e.g. eggless, nut allergy precautions). It is persisted with the order and displayed to kitchen decorators on the admin dashboard.

**Q8: How does the relationship between `Customer` and `CustomCake` work in JPA?**  
*Answer:* `CustomCake` has a `@ManyToOne(fetch = FetchType.LAZY)` relationship with `Customer`, mapped via foreign key `customer_id`. This allows retrieving all bespoke cakes submitted by any customer.

**Q9: Can unauthenticated guests submit custom cake orders?**  
*Answer:* No. `CustomCakeController.createRequest()` calls `SessionAuthHelper.requireLoggedIn(session)`. If the visitor is not signed in, an `UnauthorizedException` is thrown, prompting the frontend to display the auth modal.

**Q10: What fields are validated in `CustomCakeRequest`?**  
*Answer:* `@NotNull` on `cakeType`, `@NotBlank` on `flavor`, `@Min(1)` and `@Max(5)` on `tiers`, and `@Future` on `requiredDate`.

## 🛍️ Component 4: Retail Orders & Cart

**Package:** `com.crumb.order`  
**Owner:** Member 4 (Order & Cart Lead)

### 1. Plain-English Explanation
This component handles the retail shopping experience: adding bakery items to a cart, calculating subtotal and polymorphic delivery fees, verifying stock inventory, placing orders, rendering live order tracking via a 5-step visual timeline, and viewing past order history.

### 2. Classes & Hierarchy
- `Order` (abstract entity): Base order containing order number, customer, order date, delivery address, order items list, subtotal, discount, delivery fee, final total, status (`PENDING`, `CONFIRMED`, `BAKING`, `READY`, `DELIVERED`, `CANCELLED`), and abstract method `getDeliveryFee()`.
- `DeliveryOrder` (subclass): Surcharges a $5.00 delivery fee for regular customers, which is waived ($0.00) for VIP Gold members.
- `PickupOrder` (subclass): Sets delivery fee to $0.00 and specifies pickup counter instructions.
- `OrderItem` (entity): Line item mapping `Order` to `BakeryProduct`, storing quantity, unit price at purchase, and line subtotal.
- `OrderRepository`: Custom finders by customer ID, tracking order number, and admin status queries.
- `OrderService` / `OrderServiceImpl`: Transactional checkout processing, stock deduction, status updates, and tracking lookup.
- `OrderController`: REST endpoints at `/api/orders`.

### 3. CRUD Flow
- **Create:** User reviews cart in slide-over drawer and clicks "Proceed to Checkout". In the checkout modal, they choose Delivery or Pickup, select slot and payment method, and submit (`POST /api/orders`). The service verifies stock, builds line items, applies discounts, creates the `DeliveryOrder` or `PickupOrder`, and deducts stock.
- **Read:** User tracks order progress via `GET /api/orders/track/{orderNumber}`. Customer views past orders via `GET /api/orders/my`. Admin views all orders via `GET /api/orders`.
- **Update:** Admin advances order status (`CONFIRMED` ➔ `BAKING` ➔ `READY` ➔ `DELIVERED`) via `PUT /api/orders/{id}/status`.
- **Delete:** Customer or admin cancels a pending order via `PUT /api/orders/{id}/cancel`, which restocks the inventory back into the products table.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: How do you handle the 1-to-many relationship between Order and OrderItem?**  
*Answer:* In `Order.java`, we declare `@OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true) private List<OrderItem> items = new ArrayList<>();`. In `OrderItem.java`, we have `@ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id") private Order order;`. Saving an `Order` automatically persists its associated line items.

**Q2: How does the application ensure prices are locked at the time of purchase?**  
*Answer:* In `OrderItem`, we store `unitPrice` and `subtotal` as concrete values when the order is created. Even if a manager later updates product prices in the catalog, historic order totals and customer invoices remain unchanged.

**Q3: How is Polymorphism demonstrated in order fulfillment?**  
*Answer:* Through `Order.getDeliveryFee()`. In `PickupOrder`, the fee is always `$0.00`. In `DeliveryOrder`, the fee checks `customer.getDeliveryFeeDiscount()`. For Regular customers it returns `$5.00`, whereas for VIP Gold customers the fee is waived to `$0.00`.

**Q4: How does the 5-stage live order tracking timeline work?**  
*Answer:* In `order.js`, `renderTrackingTimeline()` inspects `order.status` against `['PENDING', 'CONFIRMED', 'BAKING', 'READY', 'DELIVERED']`. It calculates a completion percentage, animates the progress bar, highlights active nodes with a glowing pulse, and displays custom step labels based on pickup vs delivery.

**Q5: What happens to inventory when an order is placed vs cancelled?**  
*Answer:* During checkout (`placeOrder()`), `product.setStockQuantity(product.getStockQuantity() - item.getQuantity())` decreases stock. If the order is cancelled prior to baking (`cancelOrder()`), the service loops through `order.getItems()` and restores the stock quantities back to the product catalog.

**Q6: Why is `@Transactional` critical on `OrderServiceImpl.placeOrder()`?**  
*Answer:* Order placement involves multiple database writes across different tables: inserting the `Order`, inserting multiple `OrderItem` rows, deducting product inventory, and generating a booking slot. `@Transactional` guarantees atomicity: if any step fails (e.g. insufficient stock), the entire operation rolls back.

**Q7: How is the shopping cart persisted across page refreshes?**  
*Answer:* In `product.js`, the cart state is stored in browser `localStorage`. When the page loads, `loadCartFromStorage()` restores the items and updates the cart badge.

**Q8: Can a guest track an order?**  
*Answer:* Yes. `GET /api/orders/track/{orderNumber}` is a public endpoint. Anyone with the receipt order code can check the live preparation and dispatch timeline.

**Q9: How do you prevent customers from viewing orders belonging to someone else?**  
*Answer:* In `OrderController.getOrderById(id)`, the method checks `SessionAuthHelper.getCurrentUserId()`. If the user is not an Admin and does not own the order (`!order.getCustomerId().equals(userId)`), it throws a `ForbiddenException` (HTTP 403).

**Q10: What status updates are available to the admin on the order dispatch table?**  
*Answer:* The dropdown supports: `PENDING`, `CONFIRMED`, `BAKING`, `READY`, `DELIVERED`, and `CANCELLED`. Changing the dropdown triggers `PUT /api/orders/{id}/status`.

## 📅 Component 5: Bookings & Dispatch Scheduling

**Package:** `com.crumb.booking`  
**Owner:** Member 5 (Booking & Scheduling Lead)

### 1. Plain-English Explanation
This component prevents bakery kitchen overload by managing daily time slot capacity for pickup and delivery appointments. Customers schedule convenient arrival or dispatch windows, while the system checks slot availability and enforces customer tier quotas.

### 2. Classes & Hierarchy
- `Booking` (abstract entity): Contains booking reference, customer, booking date, time slot, status (`PENDING`, `CONFIRMED`, `COMPLETED`, `CANCELLED`), notes, and abstract method `getBookingType()`.
- `PickupBooking` (subclass): Sets `bookingType` to `PICKUP` and includes counter pickup instructions.
- `DeliveryBooking` (subclass): Sets `bookingType` to `DELIVERY` and includes doorstep dispatch coordinates.
- `BookingRepository`: Queries to count active bookings per date, check capacity limits, and list customer bookings.
- `BookingService` / `BookingServiceImpl`: Real-time slot capacity calculation, booking creation, quota validation, and status moderation.
- `BookingController`: REST endpoints at `/api/bookings`.

### 3. CRUD Flow
- **Create:** During checkout or custom cake scheduling, customer picks a date and time slot (`POST /api/bookings`). The service checks that the bakery slot has not exceeded maximum daily capacity (e.g., max 30 orders per day), assigns a reference code (e.g. `BKG-20261025-ABCD`), and confirms the appointment.
- **Read:** The frontend calls `GET /api/bookings/availability?date=YYYY-MM-DD` to determine if a selected date is open or full. Customer views their schedule via `GET /api/bookings/my`.
- **Update:** Admin modifies booking status (`CONFIRMED`, `COMPLETED`, `CANCELLED`) via `PUT /api/bookings/{id}/status`.
- **Delete:** Customer or admin cancels an upcoming appointment via `PUT /api/bookings/{id}/cancel`.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: How does capacity checking work to avoid overbooking the bakery?**  
*Answer:* `BookingRepository.countActiveBookingsByDate(date)` queries the total non-cancelled bookings for that calendar date. In `BookingServiceImpl`, if count exceeds `MAX_DAILY_CAPACITY` (30 bookings), `SlotAvailabilityResponse.setFullyBooked(true)` is returned, and further bookings on that day are blocked.

**Q2: How does customer tier affect booking limits?**  
*Answer:* `Customer.getMaxActiveBookings()` is polymorphic. A Regular customer is limited to 3 concurrent active bookings to prevent hoarding. A VIP Gold member can have up to 10 active bookings.

**Q3: What time slots are supported by the booking system?**  
*Answer:* The bakery supports 5 standard batch slots:
1. `08:00 AM - 10:00 AM (Early Bake)`
2. `10:00 AM - 12:00 PM (Morning Peak)`
3. `12:00 PM - 02:00 PM (Afternoon Fresh)`
4. `02:00 PM - 04:00 PM (Tea Time Batch)`
5. `04:00 PM - 06:00 PM (Evening Pickup)`

**Q4: How does the frontend date picker display available vs disabled dates?**  
*Answer:* In `booking.js`, when a customer selects a date, `checkDateAvailability(date)` queries `/api/bookings/availability`. If the response indicates full capacity, slot options are marked `disabled` with a warning message.

**Q5: What is the inheritance model for `Booking`?**  
*Answer:* JPA `InheritanceType.SINGLE_TABLE` with `@DiscriminatorColumn(name = "booking_type")`. `PickupBooking` has discriminator `PICKUP`, and `DeliveryBooking` has discriminator `DELIVERY`.

**Q6: What happens if a booking is cancelled?**  
*Answer:* Its status is changed to `CANCELLED`. It no longer counts toward the day's active booking capacity, immediately freeing up a slot for other customers.

**Q7: Can a customer create a booking in the past?**  
*Answer:* No. Both frontend datepickers set `min` to tomorrow's date, and `BookingRequest.bookingDate` is annotated with `@FutureOrPresent` to enforce server-side validation.

**Q8: What information is included in a booking reference code?**  
*Answer:* Format `BKG-YYYYMMDD-XXXX`, where `XXXX` is an uppercase random alphanumeric string. This provides an easily readable code for packing slips and order receipts.

**Q9: Where can customers review their scheduled pickup/delivery appointments?**  
*Answer:* Inside the "My Bakery Account" modal, under the "Bookings" tab, populated by calling `GET /api/bookings/my`.

**Q10: How does the admin view all scheduled bookings?**  
*Answer:* In `admin.html`, under the "Bookings & Slots" sidebar tab, which calls `GET /api/bookings` and displays references, customer names, dates, slots, and status dropdowns.

## 💳 Component 6: Payments & Customer Reviews

**Package:** `com.crumb.payment`  
**Owner:** Member 6 (Payment & Feedback Lead)

### 1. Plain-English Explanation
This component settles order transactions and captures customer feedback. It supports two payment methods: **Card Payment** (with simulated Luhn check, CVV, and expiration validation) and **Cash Payment** (pay-on-delivery or in-store cash). It generates printable receipts and provides a 5-star customer review system with admin moderation.

### 2. Classes & Hierarchy
- `Payment` (abstract entity): Base financial transaction with payment reference, customer, order ID, amount, payment date, status (`COMPLETED`, `REFUNDED`, `FAILED`), and abstract method `getPaymentMethodDetails()`.
- `CardPayment` (subclass): Adds `cardHolderName` and `cardLastFour`. Implements digital payment audit rules.
- `CashPayment` (subclass): Adds `tenderedAmount` and `changeDue`. Implements in-person settlement logic.
- `Review` (entity): Stores customer rating (1 to 5 stars), review comment, timestamp, association to `BakeryProduct`, and `approved` visibility toggle.
- `PaymentRepository` / `ReviewRepository`: Persistence and query interfaces.
- `PaymentService` & `ReviewService` (+ Impls): Transaction settlements, refund processing, review submissions, and testimonial feeds.
- `PaymentController` & `ReviewController`: REST endpoints at `/api/payments` and `/api/reviews`.

### 3. CRUD Flow
- **Create:** 
  * Payment: Created automatically at checkout (`POST /api/payments`) using Card or Cash details.
  * Review: Customer submits a 5-star review via the feedback modal (`POST /api/reviews`).
- **Read:**
  * Payment: Customer views their transaction receipts via `GET /api/payments/my`. Admin views the financial audit ledger via `GET /api/payments`.
  * Review: Storefront loads approved customer testimonials via `GET /api/reviews/testimonials`.
- **Update:**
  * Payment: Admin processes a refund via `POST /api/payments/{id}/refund`, transitioning status to `REFUNDED`.
  * Review: Admin toggles review visibility via `PUT /api/reviews/{id}/toggle`.
- **Delete:**
  * Review: Customer or admin deletes a review via `DELETE /api/reviews/{id}`.

### 4. 10 Likely Viva Questions & Model Answers

**Q1: How do you handle credit card security without violating PCI-DSS?**  
*Answer:* We never store full 16-digit card numbers or CVV security codes in the database. In `CardPayment`, only the `cardHolderName` and `cardLastFour` digits (e.g. `4242`) are persisted for customer invoice identification.

**Q2: What payment types are supported and how is this modeled in OOP?**  
*Answer:* We use inheritance with abstract class `Payment` and concrete subclasses `CardPayment` and `CashPayment`. `CardPayment` records masked card details, while `CashPayment` encapsulates cash handoff details.

**Q3: How does the refund feature work?**  
*Answer:* In `PaymentServiceImpl.refundPayment(id)`, the service verifies that the transaction exists and is currently `COMPLETED`. It updates the status to `REFUNDED`, logs the refund event, and returns the updated transaction receipt.

**Q4: How does the 5-star interactive rating system work on the frontend?**  
*Answer:* In `payment.js`, the review modal contains 5 star icons (`<i class="fa-solid fa-star">`). Hover and click event listeners dynamically fill the stars with gold color up to the selected score and update `selectedRating`.

**Q5: Why is review moderation necessary in a commercial bakery app?**  
*Answer:* To protect the bakery against spam, vulgarity, or false testimonials. Reviews default to `approved = true` for sample seeds, but new reviews can be reviewed by an administrator via `PUT /api/reviews/{id}/toggle` in `admin.html`.

**Q6: What happens if an unauthenticated user attempts to submit a review?**  
*Answer:* `ReviewController.submitReview()` enforces `SessionAuthHelper.requireLoggedIn(session)`. If no session is active, it throws an `UnauthorizedException`, and the frontend prompts the user to sign in.

**Q7: Can a customer print their payment invoice?**  
*Answer:* Yes. The Order Receipt modal includes a "Print Invoice" button that triggers `window.print()`. A dedicated `@media print` CSS stylesheet strips headers and footers to produce a clean printable paper receipt.

**Q8: What JPA annotations are used on the `Review` entity?**  
*Answer:* `@Entity`, `@Table(name = "reviews")`, `@Id @GeneratedValue`, `@ManyToOne(fetch = FetchType.LAZY)` linking to `Customer`, `@ManyToOne(fetch = FetchType.LAZY)` linking to `BakeryProduct`, and `@Column(columnDefinition = "TEXT")` for the feedback comment.

**Q9: What validation is applied to `ReviewRequest`?**  
*Answer:* `@NotNull` on `productId`, `@Min(1)` and `@Max(5)` on `rating`, and `@NotBlank @Size(min = 5, max = 1000)` on the review comment text.

**Q10: Where can the administrator inspect total gross revenue?**  
*Answer:* In `admin.html`, the top KPI card "Gross Revenue" aggregates all completed transactions from `/api/payments`, displaying the live dollar total in real time.
